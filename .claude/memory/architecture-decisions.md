# Журнал архитектурных решений (ADR)

> Каждое значимое решение (стек, БД, хостинг, способ авторизации, платёжный провайдер, деление на сервисы) — отдельной записью. Архитектура меняется только через новую запись.

## Формат
```
## ADR-NNN: <Название>
Дата: YYYY-MM-DD · Статус: предложено / принято / заменено ADR-MMM
Контекст: что за проблема и ограничения
Решение: что выбрали
Альтернативы: что рассматривали и почему нет
Последствия: что станет проще/сложнее, риски
```

## ADR-001: Модульный монолит по умолчанию
Дата: — · Статус: принято (базовое правило системы)
Контекст: небольшие команды, MVP, ограниченный бюджет на поддержку.
Решение: один деплой-юнит с модулями по доменам; бот и API — в одном сервисе, если нагрузка это позволяет.
Альтернативы: микросервисы — отвергнуты до появления независимого масштабирования или отдельных команд.
Последствия: проще деплой и отладка; при росте — выделять модули по измеренным причинам.

## ADR-002: Mobile-first веб-версия
Дата: 2026-10-29 · Статус: принято
Контекст: владелец играет и тестирует с телефона в браузере.
Решение: интерфейс проектируется под вертикальный экран телефона (~390px): поле 5 миров×2 строки должно помещаться по ширине, рука внизу с перетаскиванием пальцем, крупные касания, без ховеров как единственного способа.
Последствия: текущий concept/omut-app.html (десктоп-раскладка с горизонтальной прокруткой поля) нужно переверстать.
